# USB UDP 基准 · 2026-10-31

链路与 TCP 基准相同：USB NCM，Mac en7=192.168.77.2，RK vrusb0=192.168.77.1，MTU 1500。
iperf3 Mac 3.22 / RK 3.10.1；IPv4 UDP payload=1472 字节，预热 3 秒；接收端有效吞吐，不使用 VRI1、图像 CRC 或写盘。
SSH 和部署仍走 Wi-Fi，未修改系统 sysctl、MTU、中断亲和性或 CPU governor。

RK → Mac 最高短测约 342 MB/s，伴随 0.02381% 数据报丢失。四流 60 秒接收约 338 MB/s，
iperf3 报告 13,762,662 个数据报、0 丢包；这只描述该次观察，不能保证任意时长零丢包。
UDP 未超过此前 TCP 的约 348 MB/s。提高目标发送速率并不等于实际送出更多数据，必须看接收统计。

一次 pacing 100 μs 对比中，2 Gbit/s 的报告丢包率从约 0.35689% 降到 0.00341%；
该对比未重复，仍可能受调度和运行条件影响，不能将全部差异归因于 pacing。
Mac 全局 UDP 满 socket 缓冲丢弃计数在中间采样间从 64573 增至 65801，
表明存在接收缓冲压力，但全局计数不能精确归属到每个测试。
板端 iperf3 CPU 样本约 80%；这还不是对整条数据路径瓶颈的完整 profiling。

反向不限速测试出现明显丢包；默认配置下该测试不适合作为可靠图像数据通道。
不同端 iperf3 版本及 warmup/结束统计边界可能影响发送与接收计数对齐；丢包率按接收端报告原样保留，吞吐按接收字节/时间计算。

1472 + IPv4 20 + UDP 8 = 1500，不超过接口 MTU。iperf3 会因其大于 TCP MSS 1448 打印保守警告；
RK 发送阶段的 IP FragCreates=0、ReasmFails=0，并未因此发生 IPv4 分片。
UDP 丢的是数据报，不等同于图像帧；图像通常跨多个数据报，不能直接套用同一丢失比例。
